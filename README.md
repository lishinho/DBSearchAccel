# DBSearchAccel 开源中间件架构设计文档

DBSearchAccel是我加入蚂蚁集团第一年adindex项目的一个子项目，负责设计和实现数据库复杂查询加速中间件。

## 一、项目概述
### 1.1 项目背景
在企业级业务系统中，基于MySQL、OceanBase、PostgreSQL等关系型数据库的业务场景，随着数据量和查询复杂度提升，**复杂多参数Where子句、多表联查、大数据量表的列表查询** 极易出现慢SQL问题。传统优化手段（索引调优、SQL优化、库表分拆）存在天花板，且优化器索引选择错误、索引回查、索引数量限制等问题无法从根本上解决，导致业务页面卡顿、数据拉取失败、系统告警频发，严重影响用户体验和系统稳定性。

传统慢SQL优化链路（定位问题→优化索引→优化查询→表结构调整→缓存）仅停留在**SQL/数据库维度**，且对业务侵入性高、适配复杂场景能力弱。为此，设计一款**轻量级、配置化、无侵入**的数据库复杂查询加速中间件，融合**搜索引擎的高性能索引能力**与**关系型数据库的精准数据存储能力**，将优化维度从SQL升级为**数据索引维度**，一站式解决复杂场景慢SQL问题。

### 1.2 核心设计思想
本项目基于蚂蚁集团adindex的核心设计理念，结合开源技术栈做适配与轻量化改造，核心设计思想为：
1. **混合查询架构**：用**搜索引擎**做高性能条件过滤（查主键ID），用**关系型数据库**做精准数据详情查询，兼顾查询效率和数据准确性；
2. **实时性补全**：通过**缓存**存储业务实时增删改的主键ID，补全搜索引擎数据同步的延时短板，实现全量离线数据+实时增量数据的融合；
3. **配置化无侵入**：所有规则（路由、过滤、降级、灰度）均通过配置中心实现，业务侧无需大幅修改代码，降低接入成本；
4. **分层解耦设计**：采用模块化、分层架构，各模块职责单一、可插拔，支持灵活扩展新场景、新数据源；
5. **高可用兜底**：内置**多级降级、监控告警、数据一致性校验**能力，故障时自动兜底为原生数据库查询，保障系统稳定性。

### 1.3 项目目标
1. **性能提升**：将复杂查询的耗时从秒级降至毫秒级，消除慢SQL告警；
2. **无侵入接入**：业务侧通过配置即可完成基础接入，无需重构原有查询逻辑；
3. **多源适配**：支持MySQL、OceanBase、PostgreSQL等主流关系型数据库，兼容Elasticsearch多版本；
4. **灵活扩展**：支持新增业务场景、自定义过滤规则、自定义索引策略，适配不同企业的业务需求；
5. **高可用保障**：实现7*24小时稳定运行，故障自动降级、实时监控告警、数据一致性可校验。

### 1.4 项目定位
- **轻量级中间件**：独立部署，与原有业务系统解耦，支持单机/集群部署，容器化适配；
- **查询加速专用**：聚焦关系型数据库**复杂只读查询**加速，不介入业务写逻辑，不改变原有数据存储架构；
- **开源友好**：基于主流开源技术栈构建，文档完善，易二次开发、易运维、易集成；
- **中小企业友好**：降低企业使用搜索引擎做查询加速的技术门槛，无需专业的搜索引擎运维团队。

### 1.5 核心特性
| 特性 | 描述 |
| ---- | ---- |
| 混合查询加速 | Elasticsearch查主键+数据库查详情，规避数据库复杂查询的性能瓶颈 |
| 全量+增量数据同步 | 支持全量数据初始化索引、基于Binlog的增量数据实时同步，保证索引数据最终一致性 |
| 实时缓存补全 | AOP拦截业务增删改操作，Redis缓存实时主键ID，补全ES同步延时 |
| 配置化路由/过滤 | 基于配置中心实现场景路由、查询过滤、灰度规则，热更新无需重启服务 |
| 多级降级兜底 | 支持接口级、场景级、全局级降级，故障时自动切回原生数据库查询 |
| 多维度监控告警 | 采集QPS、延时、缓存命中率、ES查询成功率等指标，支持可视化与告警推送 |
| 自定义插件扩展 | 支持自定义数据过滤插件、自定义降级插件，适配个性化业务需求 |
| 数据一致性校验 | 支持ES索引与数据库数据的主键/字段一致性校验，定位数据同步问题 |
| 灰度放量 | 支持按商户/用户/流量的灰度准入，降低新功能上线风险 |

## 三、整体架构设计
DBSearchAccel采用**分层解耦的模块化架构**，整体分为**接入层、核心业务层、基础能力层、底层依赖层**四层，各层之间通过标准化接口交互，模块内部高内聚、模块之间低耦合，支持独立部署、灵活扩展。

### 3.1 整体架构图
```
┌─────────────────────────────────────────────────────────────────┐
│ 接入层：业务系统、前端应用                                       │
└───────────────────┬─────────────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────────────┐
│ 核心业务层：接入网关 → 路由层 → 过滤规则层 → 数据聚合层 → 索引层  │
└───────────────────┬─────────────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────────────┐
│ 基础能力层：配置中心、实时缓存、降级熔断、插件中心、数据一致性校验 │
└───────────────────┬─────────────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────────────────────────┐
│ 底层依赖层：关系型数据库、Elasticsearch、Redis、Canal、监控告警  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 架构分层职责
| 分层 | 核心模块 | 核心职责 |
| ---- | ---- | ---- |
| 接入层 | 业务系统、前端应用 | 发起查询请求，接收中间件返回的结果，无业务逻辑侵入 |
| 核心业务层-接入网关 | 统一入口、请求转发、负载均衡 | 提供统一的HTTP/SDK接口，接收业务请求，做负载均衡和请求转发 |
| 核心业务层-路由层 | 场景路由、参数标准化、接口适配 | 实现业务场景与底层索引/数据库的映射，请求参数标准化，适配不同业务接口 |
| 核心业务层-过滤规则层 | 灰度规则、自定义过滤、SQL拼接 | 实现商户/用户灰度准入、自定义数据过滤、Elasticsearch DSL动态拼接 |
| 核心业务层-数据聚合层 | 全量+增量数据拼合、主键去重 | 融合ES的全量主键和Redis的实时主键，去重后生成最终主键列表 |
| 核心业务层-索引层 | ES索引操作、Redis缓存操作 | 封装ES的索引查询、Redis的主键增删查操作，提供标准化索引能力 |
| 基础能力层-配置中心 | 配置管理、热更新、灰度发布 | 管理所有配置（路由、过滤、降级、同步），支持配置热更新和灰度 |
| 基础能力层-实时缓存 | AOP拦截、主键缓存、过期策略 | 无侵入拦截业务增删改，缓存实时主键，设置合理的过期和容量控制 |
| 基础能力层-降级熔断 | 多级降级、熔断规则、兜底逻辑 | 实现接口/场景/全局降级，熔断异常请求，兜底为原生数据库查询 |
| 基础能力层-插件中心 | 自定义插件、插件注册、插件执行 | 提供插件扩展能力，支持自定义数据过滤、自定义降级等插件 |
| 基础能力层-数据一致性校验 | 主键校验、字段校验、结果对比 | 实现ES索引与数据库的数据一致性校验，定位同步问题 |
| 底层依赖层-数据同步 | 全量同步、增量同步、异常重试 | 实现数据库到ES的全量+增量数据同步，保证索引数据最终一致性 |
| 底层依赖层-监控告警 | 指标采集、可视化、告警推送 | 采集全链路指标，实现可视化展示，异常时多渠道告警 |
| 底层依赖层-基础存储 | 数据库、ES、Redis | 提供数据存储、索引存储、缓存存储能力 |

### 3.3 架构设计原则
1. **无侵入性**：不改变业务系统的原有架构和代码逻辑，业务侧仅需通过配置/少量开发即可接入；
2. **分层解耦**：各层、各模块之间通过标准化接口交互，降低耦合度，便于独立开发、测试和部署；
3. **配置化优先**：所有可配置的规则（路由、过滤、降级、灰度）均通过配置中心实现，支持热更新；
4. **可插拔扩展**：核心能力通过插件化实现，支持自定义插件的注册和执行，适配个性化业务需求；
5. **高可用优先**：所有核心流程均有兜底逻辑，故障时自动降级，保障业务连续性；
6. **性能优先**：核心流程做轻量化设计，减少中间环节，兼顾查询效率和系统吞吐量；
7. **兼容性强**：适配主流的关系型数据库、搜索引擎和缓存组件，降低企业的迁移成本。

## 四、核心模块详细设计
### 4.1 接入网关模块
#### 4.1.1 核心职责
1. 提供**统一的接入入口**：支持HTTP/HTTPS接口和Java SDK两种接入方式，适配不同业务系统；
2. 实现**请求负载均衡**：对后端路由层节点做负载均衡，支持轮询、随机、权重等策略；
3. 实现**请求校验**：校验请求的合法性、签名、令牌，防止非法请求；
4. 实现**请求限流**：基于Sentinel做接口级限流，防止大流量压垮中间件；
5. 实现**日志记录**：记录请求的入参、出参、耗时、状态，便于问题排查。

#### 4.1.2 核心设计
- 基于**Spring Cloud Gateway**实现，轻量级、高性能，支持动态路由；
- 提供标准化的**OpenAPI文档**，便于业务侧对接；
- SDK基于**Spring Boot Starter**实现，业务侧引入依赖、配置参数即可快速接入，无代码侵入。

### 4.2 路由层模块
#### 4.2.1 核心职责
1. **业务场景标准化**：定义统一的业务场景枚举（如订单查询、商品查询、用户查询），实现场景与底层索引/数据库的映射；
2. **请求参数标准化**：封装统一的请求参数实体（`DsaRequest`），包含场景类型、查询条件、分页、排序、灰度标识等，实现参数的统一解析和传递；
3. **场景路由**：根据请求的场景类型，将请求路由到对应的索引层和数据库查询逻辑；
4. **统一返回结果**：封装统一的返回结果实体（`DsaResponse`），包含数据、分页、状态、错误信息等，实现结果的统一格式化。

#### 4.2.2 核心设计
1. 定义核心接口`DsaRouteService`，提供统一的路由方法`route(DsaRequest request)`；
2. 场景类型通过**枚举（DsaSceneType）** 定义，支持动态扩展，与配置中心的场景配置关联；
3. 请求参数支持**动态解析**，根据场景类型自动将业务查询条件转换为ES DSL查询条件；
4. 路由规则通过**配置中心**管理，支持热更新，无需重启服务。

### 4.3 过滤规则层模块
#### 4.3.1 核心职责
1. **灰度准入规则**：实现按商户ID、用户ID、IP地址的灰度放量，支持白名单/黑名单配置；
2. **自定义数据过滤**：通过插件化方式实现数据的后置过滤，满足个性化业务需求；
3. **ES DSL动态拼接**：根据标准化的查询条件，动态拼接Elasticsearch DSL语句，支持多条件、排序、分页；
4. **查询规则校验**：校验查询条件的合法性，防止无效查询和恶意查询。

#### 4.3.2 核心设计
1. **灰度规则**：基于配置中心的白名单/黑名单配置，实现**先白后黑**的校验逻辑，支持多维度灰度（商户/用户/IP）；
2. **DSL拼接**：封装**DSL构建器**（`DsaDslBuilder`），支持链式调用，动态拼接查询条件、排序、分页，兼容ES多版本；
3. **自定义过滤**：基于**插件中心**实现，定义过滤插件接口`DsaFilterPlugin`，业务侧实现接口并注册即可，支持多插件顺序执行；
4. 所有规则均通过**配置中心**管理，支持按场景配置不同的过滤规则。

### 4.4 数据聚合层模块
#### 4.4.1 核心职责
1. **全量+增量数据拼合**：将ES查询的**全量离线主键ID**与Redis缓存的**实时增量主键ID**进行拼合；
2. **主键去重与排序**：对拼合后的主键ID进行去重，根据业务需求排序，保证结果的唯一性和有序性；
3. **分页处理**：对去重排序后的主键ID进行分页，仅查询当前页的主键对应的数据库详情；
4. **空值处理**：对ES/Redis查询结果为空的场景做兜底处理，直接走数据库查询。

#### 4.4.2 核心设计
1. 采用**Set集合**实现主键去重，保证效率；
2. 排序逻辑与**业务侧查询条件**保持一致，支持多字段排序、正序/倒序；
3. 分页采用**内存分页+数据库物理分页**结合的方式，先对主键做内存分页，再通过主键做数据库物理分页，提升查询效率；
4. 支持**增量数据开关**，可通过配置中心开启/关闭，灵活适配业务的实时性需求。

### 4.5 索引层模块
#### 4.5.1 核心职责
1. **Elasticsearch索引操作**：封装ES的索引查询、新增、更新、删除操作，提供标准化的ES访问接口；
2. **Redis缓存操作**：封装Redis的主键增、删、查操作，支持列表存储、过期时间、容量控制；
3. **索引策略封装**：封装ES的索引设计策略（倒排索引、正排索引、分词索引），简化索引配置；
4. **缓存策略封装**：封装Redis的缓存策略（过期时间、容量控制、缓存刷新），保证缓存的有效性和合理性。

#### 4.5.2 核心设计
1. **ES操作**：基于**Elasticsearch Rest High Level Client**实现，封装`DsaEsService`接口，屏蔽ES底层操作细节；
2. **Redis操作**：基于**Spring Data Redis**实现，封装`DsaRedisService`接口，支持主键列表的增删查，Key为场景类型对应的固定字符串，Value为主键ID列表；
3. **ES索引设计**：默认按**业务场景**创建独立的索引，支持**倒排索引**（查询条件字段）、**正排索引**（返回字段）、**分词索引**（模糊查询字段），索引配置通过配置中心管理；
4. **Redis缓存策略**：过期时间设置为**大于ES增量同步延时，小于降级触发时间**（默认10分钟），通过配置中心控制缓存的最大主键数，避免容量溢出。

### 4.6 数据同步层模块
#### 4.6.1 核心职责
1. **全量数据同步**：将数据库中的历史全量数据同步至ES，实现索引的初始化；
2. **增量数据同步**：基于Binlog监听数据库的增删改操作，实时同步至ES，保证索引数据的最终一致性；
3. **同步异常重试**：对同步失败的任务做重试，支持定时重试和手动重试，防止数据丢失；
4. **同步进度监控**：采集全量/增量同步的进度、成功率、延时等指标，支持可视化展示。

#### 4.6.2 核心设计
1. **全量同步**：基于**DataX**实现，封装自定义的DataX任务脚本，支持按表/按条件同步，提供**全量同步控制台**，支持手动触发和定时触发；
2. **增量同步**：基于**Canal**实现，监听数据库Binlog，解析后转换为ES的增删改操作，通过**Canal Client**将数据同步至ES，支持多库多表监听；
3. **异常重试**：引入**消息队列（RocketMQ/Kafka）** 做同步任务的削峰填谷，同步失败的任务存入消息队列，做定时重试，重试失败后触发告警；
4. **同步规则**：通过配置中心管理同步的库表、字段映射、索引策略，支持按字段做索引类型配置（倒排/正排/分词）。

### 4.7 实时缓存模块
#### 4.7.1 核心职责
1. **无侵入式采集**：通过AOP拦截业务系统的增删改方法，采集实时操作的主键ID；
2. **主键缓存**：将采集到的主键ID存入Redis，实现实时增量数据的缓存；
3. **缓存清理**：根据过期时间自动清理Redis中的过期主键，支持手动清理；
4. **容量控制**：限制每个场景的缓存主键数，防止大流量导致Redis容量溢出。

#### 4.7.2 核心设计
1. **AOP拦截**：基于**Spring AOP**实现，通过自定义注解`@DsaRealTimeCache`标记业务增删改方法，无侵入式采集主键ID；
2. **主键解析**：支持配置主键字段名，自动从方法入参/返回值中解析主键ID，适配不同的业务方法；
3. **缓存更新**：业务增/改操作将主键ID加入Redis列表，业务删操作将主键ID从Redis列表中移除；
4. **容量控制**：通过配置中心设置每个场景的最大缓存数，当达到阈值时，自动剔除最早的主键ID，采用**FIFO**策略。

### 4.8 降级熔断模块
#### 4.8.1 核心职责
1. **多级降级**：实现**接口级、场景级、全局级**三级降级，满足不同粒度的兜底需求；
2. **熔断规则**：基于Sentinel实现熔断规则，支持按异常比例、慢调用比例、异常数熔断；
3. **兜底逻辑**：降级/熔断后，自动切回**原生数据库查询**，保证业务连续性；
4. **降级监控**：采集降级/熔断的次数、原因、耗时等指标，支持可视化展示和告警。

#### 4.8.2 核心设计
1. **降级规则**：基于**Sentinel** + **配置中心**实现，支持按接口/场景/全局配置降级规则，支持热更新；
   - 接口级：针对单个接口做降级，影响范围最小；
   - 场景级：针对单个业务场景做降级，影响范围中等；
   - 全局级：针对整个中间件做降级，所有请求切回数据库，仅用于极端故障场景；
2. **熔断规则**：配置慢调用阈值（默认500ms）、异常比例阈值（默认50%）、异常数阈值（默认5），达到阈值后触发熔断，熔断时长可配置；
3. **兜底逻辑**：封装**原生数据库查询接口**`DsaDbFallbackService`，降级后自动调用该接口，复用业务侧原有的数据库查询逻辑；
4. **降级恢复**：支持**自动恢复**和**手动恢复**，熔断时长结束后自动恢复，也可通过控制台手动恢复。

### 4.9 插件中心模块
#### 4.9.1 核心职责
1. **插件注册与管理**：提供插件的注册、注销、启用/禁用能力，支持插件的生命周期管理；
2. **插件执行**：根据配置的插件顺序，执行对应的插件逻辑，支持多插件链式执行；
3. **插件扩展**：提供丰富的插件扩展点，支持自定义过滤、自定义降级、自定义同步等插件。

#### 4.9.2 核心设计
1. **插件接口标准化**：定义核心插件接口，所有自定义插件均实现对应接口，如：
   - 过滤插件：`DsaFilterPlugin`，包含`execute`方法，实现数据过滤；
   - 降级插件：`DsaFallbackPlugin`，包含`fallback`方法，实现自定义降级逻辑；
   - 同步插件：`DsaSyncPlugin`，包含`sync`方法，实现自定义数据同步逻辑；
2. **插件注册**：支持**注解注册**（`@DsaPlugin`）和**配置注册**两种方式，插件自动扫描并注册到插件中心；
3. **插件执行**：封装**插件执行器**（`DsaPluginExecutor`），根据配置的插件顺序，链式执行插件，支持插件的跳过和异常处理；
4. **插件隔离**：不同场景的插件相互隔离，一个场景的插件执行失败不影响其他场景。

### 4.10 数据一致性校验模块
#### 4.10.1 核心职责
1. **主键一致性校验**：对比ES索引和数据库的主键ID，找出缺失/多余的主键；
2. **字段一致性校验**：对比ES索引和数据库中相同主键的字段值，找出不一致的字段；
3. **校验结果展示**：将校验结果可视化展示，支持导出校验报告；
4. **数据修复建议**：针对不一致的数据，提供自动/手动修复建议。

#### 4.10.2 核心设计
1. **校验方式**：支持**全量校验**和**增量校验**，全量校验用于初始化/故障恢复，增量校验用于日常监控；
   - 全量校验：批量查询ES和数据库的主键，对比找出不一致；
   - 增量校验：监听同步日志，对近一段时间的同步数据做字段校验；
2. **校验粒度**：支持**库级、表级、主键级**校验，可通过配置中心指定校验范围；
3. **性能优化**：全量校验采用**分批次、异步**执行，避免压垮数据库和ES；
4. **修复机制**：提供**自动修复**（针对增量同步的小量不一致）和**手动修复**（针对全量校验的大量不一致）两种方式，自动修复需配置白名单，防止误操作。

### 4.11 监控告警模块
#### 4.11.1 核心职责
1. **全链路指标采集**：采集中间件各模块的核心指标，实现全链路监控；
2. **指标可视化**：通过Grafana构建仪表盘，可视化展示指标变化趋势；
3. **异常告警**：设置指标阈值，异常时通过企业微信/钉钉推送告警信息；
4. **日志分析**：采集中间件的全量日志，支持日志检索、分析、可视化。

#### 4.11.2 核心设计
1. **指标采集**：基于**Prometheus + Micrometer**实现，采集的核心指标包括：
   - 接入层：QPS、请求数、成功数、失败数、平均延时、最大延时；
   - 索引层：ES查询QPS、Redis缓存命中率、ES查询成功率、Redis操作成功率；
   - 数据同步层：全量同步进度、增量同步QPS、同步成功率、同步延时；
   - 降级熔断层：降级次数、熔断次数、降级延时、兜底查询成功率；
   - 系统层：CPU、内存、磁盘、网络使用率，JVM指标；
2. **可视化仪表盘**：构建**核心指标仪表盘**、**慢查询仪表盘**、**同步状态仪表盘**、**降级熔断仪表盘**，支持多维度筛选和钻取；
3. **告警规则**：基于**AlertManager**设置告警规则，支持**阈值告警**、**趋势告警**，告警级别分为INFO、WARN、ERROR，不同级别推送不同的接收人；
4. **日志分析**：基于**ELK**实现，Logstash采集日志，Elasticsearch存储日志，Kibana做日志检索和可视化，支持按TraceID、场景类型、错误类型检索。

## 五、核心业务流程设计
### 5.1 数据同步流程（全量+增量）
**核心目标**：实现数据库到Elasticsearch的全量+增量数据同步，保证索引数据的最终一致性。
```
1. 全量同步初始化：
   a. 业务侧在配置中心配置同步的库表、字段映射、索引策略；
   b. 手动/定时触发全量同步任务，DataX从数据库拉取全量数据；
   c. 数据经过字段映射、格式转换后，批量写入Elasticsearch；
   d. 同步完成后，触发主键一致性校验，确保全量数据同步无误。

2. 增量数据实时同步：
   a. Canal监听数据库Binlog，解析出增删改操作的数据库、表、字段、主键；
   b. Canal Client将解析后的Binlog数据发送至消息队列（RocketMQ/Kafka）；
   c. 中间件的增量同步消费端从消息队列拉取数据；
   d. 数据经过字段映射、格式转换后，调用ES API执行增删改操作；
   e. 同步成功后，记录同步日志；同步失败后，存入重试队列，定时重试并触发告警。
```

### 5.2 实时缓存采集流程
**核心目标**：无侵入式采集业务实时增删改的主键ID，存入Redis，补全ES同步延时。
```
1. 业务侧在增删改方法上添加自定义注解@DsaRealTimeCache，配置主键字段名；
2. 业务执行增删改操作，Spring AOP拦截该方法；
3. AOP从方法入参/返回值中解析出主键ID；
4. 根据操作类型做相应处理：
   a. 增/改操作：将主键ID添加至Redis对应场景的主键列表；
   b. 删操作：将主键ID从Redis对应场景的主键列表中移除；
5. Redis根据配置的容量阈值，做FIFO剔除，防止容量溢出；
6. 记录缓存采集日志，包含操作类型、主键ID、缓存状态。
```

### 5.3 查询加速核心流程
**核心目标**：融合ES全量主键和Redis实时主键，实现复杂查询的性能提升，兼顾实时性和准确性。
```
1. 业务系统通过HTTP/SDK向DBSearchAccel接入网关发起查询请求，携带场景类型、查询条件、分页排序等参数；
2. 接入网关做请求校验、限流、负载均衡后，将请求转发至路由层；
3. 路由层将请求参数标准化为DsaRequest，根据场景类型做路由匹配；
4. 过滤规则层执行灰度规则校验，非灰度流量直接走原生数据库查询并返回；
5. 灰度流量通过DSL构建器，将查询条件转换为ES DSL语句；
6. 索引层调用ES API执行DSL查询，获取全量离线主键ID列表；
7. 索引层调用Redis API，获取该场景的实时增量主键ID列表；
8. 数据聚合层将两个主键列表拼合、去重、排序，按分页参数做内存分页；
9. 数据聚合层将分页后的主键ID列表传入数据库适配层，通过主键批量查询数据库详情；
10. 过滤规则层执行自定义过滤插件，对数据库查询结果做后置过滤；
11. 路由层将结果标准化为DsaResponse，经接入网关返回给业务系统；
12. 全流程记录日志和指标，用于监控和问题排查。
```

### 5.4 多级降级流程
**核心目标**：故障时自动降级，切回原生数据库查询，保障业务连续性。
```
1. 中间件各模块实时采集指标（ES查询成功率、Redis缓存命中率、延时等）；
2. 当指标达到降级/熔断阈值时，Sentinel触发对应的降级规则：
   a. 接口级降级：单个接口的异常/慢调用达到阈值，仅该接口切回数据库查询；
   b. 场景级降级：单个场景的异常/慢调用达到阈值，仅该场景切回数据库查询；
   c. 全局级降级：中间件整体异常/慢调用达到阈值，所有请求切回数据库查询；
3. 降级后，请求直接跳过ES和Redis，由降级熔断层调用原生数据库查询接口；
4. 原生数据库查询接口复用业务侧原有的查询逻辑，获取数据后返回给业务系统；
5. 降级期间，监控模块实时采集降级指标，触发告警推送；
6. 当指标恢复正常后，自动/手动取消降级，恢复正常的查询加速流程。
```

## 六、配置化设计
DBSearchAccel遵循**配置化优先**的设计原则，所有规则均通过**Nacos/Apollo**配置中心管理，支持**热更新**、**灰度发布**、**按环境配置**，无需重启服务即可生效。

### 6.1 配置层级
配置分为**全局配置、场景配置、模块配置**三级，优先级为：场景配置 > 模块配置 > 全局配置，支持按需覆盖。
1. **全局配置**：对整个中间件生效的配置，如Redis过期时间、ES连接参数、监控告警阈值等；
2. **场景配置**：对单个业务场景生效的配置，如场景的灰度规则、DSL拼接规则、过滤插件等，可覆盖全局配置；
3. **模块配置**：对单个模块生效的配置，如数据同步的重试次数、降级的熔断阈值等，可覆盖全局配置。

### 6.2 核心配置项
#### 6.2.1 全局配置（dsa.global.*）
| 配置项 | 类型 | 默认值 | 描述 |
| ---- | ---- | ---- | ---- |
| dsa.global.es.addr | String | 127.0.0.1:9200 | ES集群地址，多个地址用逗号分隔 |
| dsa.global.redis.addr | String | 127.0.0.1:6379 | Redis地址 |
| dsa.global.redis.expire | Integer | 600 | Redis缓存过期时间（秒），默认10分钟 |
| dsa.global.redis.max-count | Integer | 10000 | 每个场景的Redis缓存最大主键数 |
| dsa.global.monitor.enabled | Boolean | true | 是否开启监控指标采集 |
| dsa.global.alert.enabled | Boolean | true | 是否开启告警推送 |
| dsa.global.fallback.enabled | Boolean | true | 是否开启降级兜底 |

#### 6.2.2 场景配置（dsa.scene.{sceneType}.*）
| 配置项 | 类型 | 描述 |
| ---- | ---- | ---- |
| dsa.scene.{sceneType}.enabled | Boolean | 是否开启该场景的查询加速 |
| dsa.scene.{sceneType}.es.index | String | 该场景对应的ES索引名 |
| dsa.scene.{sceneType}.db.table | String | 该场景对应的数据库表名 |
| dsa.scene.{sceneType}.gray.white-list | List<String> | 灰度白名单，如商户ID/用户ID |
| dsa.scene.{sceneType}.gray.black-list | List<String> | 灰度黑名单，如商户ID/用户ID |
| dsa.scene.{sceneType}.filter.plugins | List<String> | 该场景的自定义过滤插件列表 |
| dsa.scene.{sceneType}.dsl.fields | Map<String, String> | 场景查询字段与ES字段的映射 |

#### 6.2.3 模块配置（dsa.module.*）
| 配置项 | 类型 | 默认值 | 描述 |
| ---- | ---- | ---- | ---- |
| dsa.module.sync.full.cron | String | 0 0 1 * * ? | 全量同步的定时任务Cron表达式 |
| dsa.module.sync.increment.retry-count | Integer | 3 | 增量同步的重试次数 |
| dsa.module.circuit.grade | String | ERROR_RATIO | 熔断策略，支持ERROR_RATIO/SLOW_CALL_RATIO/ERROR_COUNT |
| dsa.module.circuit.error-ratio | Double | 0.5 | 异常比例阈值，默认50% |
| dsa.module.circuit.slow-call-threshold | Integer | 500 | 慢调用阈值（毫秒），默认500ms |

### 6.3 配置热更新
配置中心与中间件做实时联动，配置修改后**10秒内**自动生效，无需重启服务。实现方式：
1. 基于Nacos/Apollo的**配置监听**能力，中间件启动时注册配置监听器；
2. 配置发生变化时，监听器触发配置刷新事件，更新中间件内存中的配置；
3. 核心模块（路由层、过滤规则层、降级熔断层）实时读取内存配置，保证配置生效。

## 七、高可用设计
### 7.1 部署高可用
1. **集群部署**：所有核心模块均支持集群部署，避免单点故障，接入网关做负载均衡；
2. **容器化**：支持Docker/K8s部署，实现服务的自动扩缩容、故障重启；
3. **多可用区部署**：支持跨可用区部署，提升服务的容灾能力；
4. **数据持久化**：ES采用集群模式并开启数据持久化，Redis采用主从+持久化模式，防止数据丢失。

### 7.2 流程高可用
1. **多级降级**：接口/场景/全局三级降级，故障时自动兜底为原生数据库查询；
2. **熔断保护**：对异常/慢调用请求做熔断，防止故障扩散，保护中间件和数据库；
3. **异常重试**：数据同步、ES查询、Redis操作等核心流程均做异常重试，提升成功率；
4. **空值兜底**：ES/Redis查询结果为空时，直接走数据库查询，保证数据返回。

### 7.3 数据高可用
1. **最终一致性**：通过全量+增量数据同步，保证ES索引与数据库的数据最终一致性；
2. **数据校验**：支持全量/增量数据一致性校验，及时发现并修复数据不一致问题；
3. **同步重试**：增量同步失败的任务存入消息队列，做定时重试，防止数据丢失；
4. **缓存容错**：Redis故障时，自动跳过缓存层，仅用ES查询，保证查询加速流程继续运行。

### 7.4 监控告警高可用
1. **多维度监控**：全链路指标采集，实时掌握中间件运行状态，提前发现潜在问题；
2. **多渠道告警**：支持企业微信/钉钉/邮件多渠道告警，保证告警信息及时触达；
3. **告警分级**：按问题严重程度分为INFO/WARN/ERROR三级，不同级别推送不同的接收人；
4. **日志兜底**：全流程详细日志记录，支持按TraceID检索，便于故障快速定位。

## 八、部署与接入设计
### 8.1 部署方式
DBSearchAccel支持**三种部署方式**，适配不同企业的运维体系：
1. **单机部署**：适用于开发/测试环境，所有模块部署在单台服务器，快速搭建、便于调试；
2. **集群部署**：适用于生产环境，核心模块（接入网关、路由层、索引层）集群部署，底层依赖（ES、Redis、数据库）采用集群模式；
3. **容器化部署**：适用于云原生环境，基于Docker/K8s部署，支持自动扩缩容、滚动更新、故障自愈。

### 8.3 业务接入方式
遵循**无侵入、低开发**的原则，根据业务需求的复杂度，分为**四种接入场景**，开发量从无到有梯度适配，与原adindex的接入场景保持一致。

#### 场景1：基础接入（无开发量，仅配置）
**适用场景**：业务查询逻辑无变更，仅需对现有复杂查询做加速。
**接入步骤**：
1. 在配置中心配置场景信息（场景类型、ES索引、数据库表名）；
2. 在配置中心配置灰度规则（白名单/黑名单）；
3. 业务侧通过HTTP/SDK替换原有数据库查询接口，无需修改代码；
4. 开启灰度放量，验证查询效果。

#### 场景2：增加返回字段（少量开发量）
**适用场景**：在现有查询结果中增加返回字段，不修改查询条件。
**接入步骤**：
1. 在配置中心更新场景的字段映射配置，添加新增字段；
2. 执行ES索引的字段更新，新增字段配置为正排索引；
3. 业务侧在数据库查询逻辑中增加返回字段，无需修改中间件代码；
4. 验证查询结果，确认新增字段正常返回。

#### 场景3：增加查询条件/新增SQL（中等开发量）
**适用场景**：在现有场景中增加查询条件，或新增一条查询SQL。
**接入步骤**：
1. 在配置中心更新场景的DSL字段映射，添加新增查询条件的映射；
2. 若新增查询条件需要模糊查询，在ES中配置分词索引；
3. 若需要自定义过滤，开发过滤插件并注册到插件中心；
4. 在配置中心配置插件执行规则，开启灰度放量验证。

#### 场景4：新增业务场景（大量开发量）
**适用场景**：新增非原有业务的查询场景，需要全新的索引和查询逻辑。
**接入步骤**：
1. 在配置中心新增场景配置，定义场景类型、ES索引、数据库表名；
2. 配置数据同步规则，执行全量数据同步，初始化ES索引；
3. 若需要实时缓存，在业务侧增删改方法上添加@DsaRealTimeCache注解；
4. 若需要自定义过滤/降级，开发对应的插件并注册；
5. 配置灰度规则，开启小流量灰度验证，验证通过后全量放量。

## 九、后续规划
### 9.1 短期规划（V1.0-V1.5）
1. 完成核心模块的开发与测试，发布V1.0正式版；
2. 完善文档（开发文档、部署文档、接入文档、运维文档）；
3. 适配更多的数据源（如SQL Server、MongoDB）；
4. 增强插件中心能力，提供更多的官方插件（如数据脱敏、数据聚合）；
5. 完善运维控制台，支持可视化配置、数据同步、一致性校验、降级恢复。

### 9.2 中期规划（V2.0-V2.5）
1. 支持**多租户**能力，适配SaaS模式的企业需求；
2. 增强**智能索引推荐**能力，根据业务查询条件自动推荐ES索引策略；
3. 支持**SQL直接解析**，业务侧可直接传入SQL，中间件自动解析为ES DSL，进一步降低接入成本；
4. 增强**数据一致性**能力，实现ES与数据库的实时双向同步；
5. 适配**云原生**，提供K8s Operator，实现中间件的自动化部署、运维和扩缩容。

### 9.3 长期规划（V3.0+）
1. 引入**AI能力**，实现慢SQL自动识别、自动优化、自动配置索引；
2. 支持**多搜索引擎**适配（如Milvus、Solr），提供更丰富的索引能力；
3. 构建**生态体系**，鼓励社区贡献插件、适配新的数据源、完善文档；
4. 提供**全链路低代码平台**，实现业务场景的可视化配置、一键接入、实时监控；
5. 支持**边缘部署**，适配边缘计算场景的查询加速需求。
